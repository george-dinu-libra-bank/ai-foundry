09:50 · Theory · 25′

Microsoft Foundry & what an LLM gateway does

Yesterday you saw where Microsoft Foundry sits on the map of Azure; today we use it. The mental model that makes everything click is the gateway. A raw model API answers exactly one question: "here are tokens, give me tokens back." Everything an organization actually needs around that — who may call, how much, with what safeguards, at what cost, observed how — is missing by design. An LLM gateway is the layer that adds it: a managed front door between your applications and the models.

The gateway pattern: applications never talk to "the model" — they talk to a governed deployment behind one authenticated, metered, filtered front door.

Each gateway concern maps to something concrete you will touch today. Identity: calls are authorized by Entra ID roles, not by secrets in code — your az login this morning is literally your access badge. Quota: every deployment carries a tokens-per-minute (TPM) and requests-per-minute budget; exceeding it returns HTTP 429, which is why production code retries politely (Session 3's topic). Content filtering: prompts and completions pass safety classifiers — in a bank, configurable but never optional. Metering: every response reports its exact token consumption, the number your cost model is built on. Observability: requests, latencies and errors land in Azure Monitor, where an operator can answer "what is happening right now?" — a question you will personally ask in Session 6.

One term deserves precision: a deployment is your named instance of a model behind the gateway — the catalog model (gpt-5.1) plus your configuration (deployment name, type, quota, filters). Code never calls "GPT"; it calls your deployment by its name. That indirection is what lets an organization upgrade, throttle or swap models without touching application code.

The three lanes: provider-direct, through Azure, or local

Every organization consuming LLMs chooses between three lanes, and the choice is rarely about model quality — the same or similar models exist in all three. It is about where data flows, who governs the door, and what you must operate yourself.

Lane 1 · Provider-direct
app → api.openai.com
Provider's infrastructure & terms
API-key auth · newest features first
Lane 2 · Through Azure (Foundry)
app → your endpoint, your region
Your tenant's boundary
Entra ID · quotas · filters · one bill
Lane 3 · Local / self-hosted
app → your own hardware
Open-weight models (Foundry Local, Ollama)
nothing leaves the machine

Three lanes to an LLM. The decision is about boundaries and operations, not model quality.

DimensionProvider-directThrough AzureLocal

FitsPrototypes, consumer appsEnterprises, regulated industriesAir-gapped, edge, data-cannot-move cases

Why lane 2 for a bank is nearly axiomatic: banking regulation demands knowing where data resides, who accessed what, and proving both to an auditor. Lane 2 inherits all three from the platform (region pinning, Entra ID, Azure's audit surface); lane 1 makes each a negotiation, lane 3 makes each a construction project. Lane 3 still matters — genuinely sensitive data that must never leave a machine, offline scenarios, and cost experiments with small models — which is why Foundry ships Foundry Local to run catalog models on your own hardware. Know all three lanes; default to the governed one.

The deployment path. After the playground answers, every remaining problem is client-side — which is exactly where the lab picks up.

What to notice while I click. In the catalog: the task filter (chat vs embeddings), the provider spread, context-window sizes, and per-token prices — input and output priced separately. In the deploy dialog: the deployment name (what your code will reference), the type (global standard pay-as-you-go for us; regional when residency pins traffic; provisioned throughput for reserved capacity), and the TPM quota slider — the budget that protects you from yourself. In the playground: the system-prompt box (persona lives here), the parameter panel (temperature, max tokens), and the view of the conversation as raw messages — the exact structure your code sends in the lab.

11:00 · Live coding · 15′

The first authenticated call, line by line

Eight lines, every one earning its place. I write and run this in front of you; in twenty-five minutes you run it yourself. Read it top to bottom before we dissect it:

hello_foundry.py 
from azure.ai.inference import ChatCompletionsClient
from azure.identity import DefaultAzureCredential

ENDPOINT = "https://<your-project>.services.ai.azure.com/models"   # Foundry portal → Overview

client = ChatCompletionsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())

reply = client.complete(
    model="gpt-5.1",                          # your DEPLOYMENT name, not "the model"
    messages=[
        {"role": "system", "content": "You are a precise assistant. Answer in two sentences."},
        {"role": "user", "content": "What does an LLM gateway add on top of a raw model API?"},
    ],
)

print(reply.choices[0].message.content)
print(reply.usage)                            # prompt_tokens, completion_tokens — the meter

The dissection, line by line. The imports pair the inference client with the identity library — model access and authentication are separate concerns, deliberately. The endpoint is your project's front door from the portal's Overview page; note there is no key in this file, and there never will be. DefaultAzureCredential is the magic that isn't magic: it probes a fixed chain of identity sources — environment variables, managed identity, VS Code, the Azure CLI you signed into this morning, Azure PowerShell — and uses the first that yields a token. Locally that is your CLI login; in Session 6, deployed to the cloud, the identical line will find a managed identity instead. Same code, both worlds.

The complete() call carries the two ideas from yesterday made concrete: model= names your deployment (the gateway indirection — this string is yours, not OpenAI's), and messages= is the context window being assembled — a system role setting standing behaviour, a user role carrying the question. The response gives you the generated message and, riding along, the usage object: exact prompt and completion token counts. That object is the raw material of cost engineering, and from today it appears in everything we build.

11:15 · Theory · 10′

How we'll build from Session 3: spec-driven, AI-assisted

Tomorrow we build a real application — and we will not type most of it. Modern engineering teams increasingly delegate implementation to AI coding agents (tools like GitHub Copilot and Claude Code that read a codebase, plan, and write code across files). What separates professionals from hobbyists in that world is not typing speed; it is specification discipline. The failure mode has a name — vibe coding: prompting an agent with a vague wish, accepting whatever appears, and iterating by complaint. It feels fast and produces systems nobody can explain, extend or trust.

Spec-driven development inverts the flow: you write down what should exist — goals, interfaces, constraints, non-goals — the agent proposes a plan, you review the plan, the agent implements, and you verify the result against the spec before anything is committed. The human owns intent and judgment; the agent owns keystrokes. Tomorrow you will watch the entire loop run for real, building the skeleton of Libra Assist from a one-page spec:

The spec-driven loop. Every arrow survives because the artifact before it is written down — the spec is the contract.

Why this is in a bank's course

Reviewability. A spec and a plan are documents a colleague — or a regulator — can read. "The AI wrote it and it seems to work" is not a sentence you will ever say in production; "it implements this spec, verified point by point" is.

Step 3 — Libra Assist speaks its first words (≈5′)

Change the system prompt — nothing else — and observe how completely it changes the product:

hello_foundry.py · the persona line 
{"role": "system", "content":
    "You are Libra Assist, the internal AI assistant of a retail bank. "
    "Answer precisely and professionally, in English, two short paragraphs maximum. "
    "If a question needs data you don't have, say exactly what is missing."},

Ask it something a colleague would: "A customer says their card is blocked — what should I check first?" This one line is the beginning of the persona we will ground, measure and equip with tools all week.

Step 4 — turn the two dials (≈8′)

Run the same question three ways and note what changes: temperature=0.0, then temperature=1.0 (run it twice — is the answer identical?), then add max_tokens=30 and watch the answer stop mid-thought. Check reply.choices[0].finish_reason: "stop" means the model finished; "length" means you cut it off — a distinction production code must handle.

Step 5 — read the meter like an engineer (≈7′)

add to the end 
u = reply.usage
print(f"prompt={u.prompt_tokens}  completion={u.completion_tokens}  total={u.total_tokens}")
print(f"a day of 10,000 such calls ≈ {10_000 * u.total_tokens:,} tokens")

That last number, multiplied by the per-million-token price you saw in the catalog, is how AI features get budgeted. From now on, every lab prints its own consumption — cost awareness is a habit, not a chapter.

Stretch goals — if you're ahead

Streaming. Long answers should render as they generate, token by token — the pattern behind every chat UI you have ever used:

stream.py 
stream = client.complete(
    model="gpt-5.1", stream=True,
    messages=[{"role": "user", "content": "Explain, step by step, how an IBAN is validated."}],
)
for update in stream:
    if update.choices and update.choices[0].delta.content:
        print(update.choices[0].delta.content, end="", flush=True)

Embeddings. Reproduce yesterday's geometry demo yourself: embed "my card is blocked" and "frozen debit card" with EmbeddingsClient and model="text-embedding-3-small", and compute their cosine similarity — Session 5 will thank you.

Conclusions

What today changed

This morning "the model" stopped being an abstraction. You now hold the gateway model of enterprise AI — identity, quota, filtering, metering and monitoring wrapped around every call — and you have felt it concretely: your CLI sign-in was the badge, your deployment name was the indirection, the usage object was the meter. You can argue the three lanes like an architect and default to the governed one for bank work. And Libra Assist exists — one system prompt old, already answering in character from your own script. Tomorrow it becomes an application: a spec on one page, an AI agent building the skeleton, and by noon a chat interface on your own machine talking to your own deployment.

Takeaways

If you remember six things

1. A gateway turns a raw model API into something an organization can govern: identity, quota, filters, metering, monitoring.

2. Code calls a deployment by name, never "the model" — that indirection is how enterprises swap and throttle models safely.

3. Three lanes — provider-direct, through Azure, local. The choice is about boundaries and governance, not model quality.

4. DefaultAzureCredential = the same code authenticating via your CLI login today and a managed identity in production.

5. Every response carries its own meter — read usage, always. Cost is an engineering metric.

6. Spec first, then plan, then code, then verify. The spec is the contract — vibe coding is the anti-pattern.
