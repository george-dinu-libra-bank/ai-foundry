10:00 · Theory · 10′

Why Python is the language of AI

Python did not win artificial intelligence because it is the fastest language — it is not — but because it accumulated, layer by layer over two decades, the entire numerical and machine-learning ecosystem. The foundation was laid by NumPy, which gave Python an efficient n-dimensional array and, crucially, a convention: heavy numerical work is executed not by the Python interpreter but by compiled C and Fortran kernels (BLAS/LAPACK) that Python merely orchestrates. Everything since — pandas for tabular data, scikit-learn for classical machine learning, PyTorch for deep learning, Hugging Face Transformers for pretrained models — follows the same pattern and interoperates through the same array conventions.

Two decades of compounding: each layer of the scientific Python stack builds on the conventions of the previous one.

This history produced a powerful network effect: research papers publish Python code, university courses teach in Python, and every model provider — OpenAI, Microsoft, Anthropic, Google, Meta — ships its Python SDK first and most completely. Architecturally, Python plays the role of a glue language: the interpreter executes orchestration logic — reading configuration, calling APIs, moving data between systems — while the performance-critical work happens elsewhere, in compiled kernels, on GPUs, or, in this course, on the other side of an HTTPS call inside an Azure datacenter. Python coordinates; optimized systems compute. And it spans the whole lifecycle: the same language runs in a Jupyter notebook where experiments live and in the production service that ships — no rewrite between "it works on my laptop" and "it runs for users".

10:10 · Theory · 20′

Generative AI: the concepts that carry the module

Classical software is programmed: a developer writes explicit rules, and the system does exactly what the rules say. Machine learning inverts this: a model's behaviour is learned from data, encoded as numerical parameters adjusted during training to minimize prediction error. A large language model (LLM) is the current apex of that approach — a neural network, almost always based on the transformer architecture (introduced in 2017), trained on enormous text corpora with a deceptively simple objective: predict the next token.

That objective explains almost everything about how these systems behave. Generation is autoregressive: the model produces one token, appends it to the input, and predicts again — a loop, not a lookup. What you experience as fluent writing is a long chain of conditional probability distributions being sampled, token by token.

Inside the transformer

A transformer is a stack of identical layers, each combining two operations. Self-attention lets every token compute a relevance-weighted view of every other token in the input — this is how "it" finds its referent and how "rate" learns whether the sentence is about interest or speed. A feed-forward network then transforms each of those contextualized representations independently. Stack the pair dozens of times and the representations grow progressively more abstract; a final projection turns the last layer into a probability distribution over the entire vocabulary — the next-token prediction.

The transformer stack. "Large" in LLM counts the learned parameters inside these layers — from billions to trillions of weights.

The learned parameters — the weights — are where all capability lives; a model file is essentially those numbers. Inference is one forward pass through the stack per generated token, which is why the work is dominated by matrix multiplication, why it runs on GPUs, and why latency grows with answer length.

How a model is made

Training happens in stages, and each stage explains a behaviour you will observe all module long. Pretraining — next-token prediction over web-scale corpora — builds capability and knowledge, and fixes the knowledge cutoff: the model knows nothing after its data ends. Supervised fine-tuning teaches the instruction-following format from curated example dialogues. Preference alignment (methods such as RLHF — reinforcement learning from human feedback) tunes outputs toward what human raters prefer — the origin of both the model's helpfulness and its characteristic failure modes: refusals, hedging, and the eagerness-to-please that can shade into flattery. What you call gpt-5.1 is the artifact of all three stages, served behind an endpoint.

Tokens: the unit of everything

Models do not read characters or words; they read tokens — subword fragments produced by algorithms such as byte-pair encoding (BPE). "Banking" may be one token; a rare Romanian compound may be five. Three consequences matter to an engineer: cost (providers price per token, input and output separately), latency (each output token is a full pass through the model, which is why long answers stream), and capacity — the limit on how much the model can consider at once, which brings us to the context window.

The context window: anatomy of a request

The context window is the maximum number of tokens the model can attend to in one call — its working memory. Everything you want the model to consider must be serialized into it, and every token inside it is billed on every call. A real request is therefore a composed artifact with a budget:

Context window · the token budget (tens of thousands to millions of tokens)
System prompt

Conversation history

Retrieved documents

Anatomy of one request. The completion the model writes back consumes output tokens on top of this input budget.

Two engineering habits follow directly. Because history is re-sent each turn, long conversations grow linearly in cost — production systems truncate or summarize. And because instructions, examples (few-shot prompting) and evidence all compete for the same budget, prompt design is partly a resource-allocation problem — the discipline Session 4 turns into measurement.

Embeddings: meaning as geometry

Alongside generative models sit embedding models, which map text to a dense vector representation — a point in a high-dimensional space. The model this course deploys, text-embedding-3-small, produces 1536-dimensional vectors with a learned property: texts with similar meaning land close together, where "close" is measured by cosine similarity between vectors. Similarity search over embeddings is what powers semantic search and retrieval-augmented generation — Session 5's core.

Determinism, temperature and sampling

The model's output layer is a probability distribution; sampling chooses the actual token. The temperature parameter rescales that distribution before the choice: low temperature sharpens it toward the single most probable token (near-deterministic, focused, repetitive at the extreme), high temperature flattens it (varied, creative, riskier). A companion parameter, top-p, restricts sampling to the smallest set of tokens whose probabilities sum to p. One practical caveat: even at temperature 0, bit-identical runs are not guaranteed — floating-point arithmetic and server-side batching introduce small nondeterminism. Treat determinism as a dial, not a promise.

Temperature ≈ 0Temperature ≈ 1
BehaviourPicks the most probable continuation almost every timeSamples broadly across plausible continuations
SuitsExtraction, classification, structured output, reproducible testsDrafting, brainstorming, variety in tone

Capabilities and limits

A next-token predictor optimizes plausibility, not truth. When the training distribution offers no strong signal, the model produces confident, fluent, wrong text — hallucination (more precisely, confabulation). Add the fixed knowledge cutoff, biases inherited from the corpus, and sampling's inherent variability, and the engineering agenda of this module writes itself: ground the model in real documents, measure output quality systematically, and put guardrails around actions.

Fluent is not correct

An LLM states falsehoods with the same confidence as facts. This is not a reason to avoid the technology — it is the reason this course exists. Grounding (Session 5), systematic evaluation (Session 4) and guardrails (Session 6) are what turn a plausible-text generator into a dependable system.

Demo 1 — tokens made visible

The tokenizer is public — we can run the exact algorithm the model uses and count what a sentence costs. Watch what happens to English versus Romanian, and to rare words versus common ones:

demo_1_tokens.py 
import tiktoken

enc = tiktoken.get_encoding("o200k_base")   # the tokenizer family behind recent GPT models

for text in [
    "The card is blocked.",
    "Cardul este blocat.",
    "Retrieval-augmented generation",
]:
    tokens = enc.encode(text)
    print(f"{len(tokens):>3} tokens | {text}")

The observation that matters: token counts — not character counts — are what you pay for and what fills the context window. Non-English text and rare terminology tokenize less efficiently, which has real cost consequences for a Romanian bank.

Demo 2 — talking to gpt-5.1, twice

One authenticated call to the deployed model, then the same question at two temperatures. Watch the role of the system prompt — and how variability is a parameter, not an accident:

demo_2_chat.py 
from azure.ai.inference import ChatCompletionsClient
from azure.identity import DefaultAzureCredential

client = ChatCompletionsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())

for temperature in (0.0, 1.0):
    reply = client.complete(
        model="gpt-5.1",
        temperature=temperature,
        messages=[
            {"role": "system", "content": "You are a precise banking assistant. Two sentences maximum."},
            {"role": "user", "content": "Explain what an IBAN is."},
        ],
    )
    print(f"--- temperature={temperature} ---")
    print(reply.choices[0].message.content)

Demo 3 — meaning as geometry

Finally, the embedding space from the previous section, for real: four phrases, their vectors, and the cosine-similarity matrix. Predict which pair wins before the numbers print:

demo_3_embeddings.py 
import numpy as np
from azure.ai.inference import EmbeddingsClient
from azure.identity import DefaultAzureCredential

client = EmbeddingsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())

phrases = ["my card is blocked", "frozen debit card",
           "mortgage interest rate", "the weather in Cluj"]

vectors = [np.array(item.embedding)
           for item in client.embed(model="text-embedding-3-small", input=phrases).data]

def cosine(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

for i, a in enumerate(phrases):
    for j, b in enumerate(phrases):
        if i < j:
            print(f"{cosine(vectors[i], vectors[j]):.3f}  {a!r} vs {b!r}")

11:00 · Theory · 15′

The cloud is not just someone else's computer

Strip the marketing and cloud computing is this: computing capacity — servers, storage, networking, and increasingly entire managed platforms — consumed as a metered service over the network rather than owned as hardware. Owning servers means capacity planning years ahead, paying for peak load around the clock, and operating everything from firmware to backups yourself. The cloud model replaces that with three structural shifts: elasticity (capacity pooled across many tenants through virtualization scales with demand and back), a new cost shape (capital expenditure becomes metered operating expenditure — which is why cost becomes an engineering metric), and managed services — you rent outcomes ("a database", "a model endpoint") operated to a contractual SLA, and the unit of thought moves up from servers to capabilities.

The anatomy of a cloud application

Nearly every cloud application — including the one you will build — converges on the same layered shape: a client, a stateless application tier, a set of managed data and AI services behind it, and three cross-cutting concerns (identity, secrets, observability) that touch everything:

The shared-responsibility model

What the cloud never removes is responsibility for your side of the system. Security and operations are split between provider and customer along a boundary that depends on the service model — infrastructure (IaaS), platform (PaaS), or software (SaaS) as a service. Read the matrix column by column — and notice the row that never changes hands: identity and data are yours in every column.

11:15 · Walkthrough, part one

A guided tour of Azure, section by section

Azure is Microsoft's cloud platform: more than 60 regions offering compute, storage, networking, data and AI services under one management, identity and billing model. In the live walkthrough I take you through it in four passes — the physical layer, the identity layer, the resource model, and the tools. Each subsection below matches what you will see on screen, so this page works as your revisit guide.

1 · The global infrastructure

At the bottom sit the physical facilities. A region is a set of datacenters in one geographic area (West Europe, Sweden Central, …) connected by low-latency links; many regions are organized into availability zones — physically separate datacenter groups with independent power, cooling and networking, so that a facility-level failure does not take the region down. Regions are joined by Microsoft's private fiber backbone, and many form region pairs for disaster recovery. Why it matters to you: the region you deploy into determines latency to your users, which services and models are available, the price sheet — and, decisive in banking, where the data physically resides for residency and sovereignty obligations.

2 · Identity: the tenant and Microsoft Entra ID

Before any resource exists, there is a directory. A tenant is an organization's dedicated instance of Microsoft Entra ID (formerly Azure Active Directory) — the identity system holding every user, group, application and managed identity. Every sign-in and every API call in Azure is authenticated against the tenant, and authorization is granted through role-based access control (RBAC): an assignment of a role (what actions are allowed) to an identity at a scope (where). Remember the phrase identity is the security perimeter — in the cloud there is no firewall around everything; there are identities and the roles they hold. This is also why this course never touches an API key: our code will authenticate as an identity, keylessly.

3 · The resource hierarchy

Everything you create in Azure is a resource — a database, a model deployment, a container app. Resources live in resource groups, the unit of lifecycle: things that are deployed, secured and deleted together share a group. Resource groups belong to a subscription — the boundary for billing, quotas and policy, and the classic unit handed to a team or project. Subscriptions can be organized under management groups for organization-wide governance. Two mechanisms ride this tree: RBAC assignments and Azure Policy rules applied at any level inherit downward, and tags (key–value labels) cut across it for cost attribution. When something in Azure confuses you, the first question is always: where in this hierarchy am I?

All management flows through one control plane — Azure Resource Manager (ARM), a REST API that every tool below ultimately calls. Because the control plane is uniform, anything you can click can also be scripted, templated and audited; teams describe entire environments declaratively (ARM/Bicep templates, Terraform) and let the platform converge to the description. 11:15 · Walkthrough, part two

Microsoft Foundry: a tour of the AI platform

Microsoft Foundry is the umbrella platform where Azure's AI work happens: one place to browse and deploy models, build and run agents, connect knowledge sources, evaluate quality and monitor usage. It is the current name of a product line you may know under older names — Azure's Cognitive Services became Azure AI services, gained a unified portal as Azure AI Studio, was renamed Azure AI Foundry, and in late 2025 became simply Microsoft Foundry. The renames matter only so you can read older documentation; the direction is one platform consolidating what used to be a dozen separate services.

Foundry shows two faces. In the Azure portal you manage it as infrastructure — the resource, its networking, identity and cost, sitting in the resource hierarchy you just learned. In the Foundry portal (ai.azure.com) you work in it as a builder — projects, model catalog, playground, agents, evaluations. Same objects, two lenses: one for governance, one for building. In the walkthrough we open both.

Foundry vs Azure OpenAI — the distinction that matters

Click + Create on the Azure OpenAI blade and the portal offers two choices: "Foundry (Recommended)" and "Azure OpenAI". They are two different resource types with a real history. Azure OpenAI arrived first: a dedicated service exposing OpenAI's models (GPT chat models, o-series reasoning models, embeddings, image and audio models) under Azure's enterprise contract — your data is not used to train the models, traffic stays inside your tenant's boundary, private networking and content filters apply. Thousands of organizations, banks included, built on it and hold estates of Azure OpenAI resources today. Foundry is the platform that grew around and beyond it: the same OpenAI models, plus the multi-vendor catalog, plus projects, agents, evaluations and tracing — one resource for the whole AI application lifecycle rather than one model family.

Takeaways

If you remember six things

1. Python won AI by network effect — every model, library and SDK meets you there, and Python orchestrates while compiled kernels compute.

2. LLMs predict the next token: context is their working memory, tokens are your cost, and generation is a loop.

3. Fluent is not correct — grounding, evaluation and guardrails are what make AI dependable.

4. Cloud = elasticity + managed services + shared responsibility; identity and data are always yours.

5. Azure in one line: resource → resource group → subscription → tenant, with RBAC and policy inheriting down.

6. Microsoft Foundry is the platform; Azure OpenAI is one lane inside it. New work starts on Foundry.

Assignment

Before Session 2: environment check

≈ 30 minutes · do this today if you can

Session 2 is hands-on from the start. Five checks now save us thirty minutes tomorrow.

  1. Install Visual Studio Code.
  2. Install Python 3.11 or newer — on Windows, tick "Add python.exe to PATH" during setup.
  3. In VS Code, install the Python extension (by Microsoft).
  4. Verify: open a terminal and run python --version — you should see 3.11+.
  5. Sign in to the Azure portal with the account provided for the academy, and confirm the portal opens.

If anything fails

Don't spend your evening on it. Note the exact error message and bring it along — the first minutes of Session 2 are reserved for getting every environment green, together.
