09:30 · Theory · 10′

Where we are, and where today lands

Inventory after two sessions: a governed model deployment (gpt-5.1) and an embedding deployment behind your project's endpoint; a working keyless toolchain on every laptop (az login → DefaultAzureCredential); a script that speaks as Libra Assist; and the habit of reading the token meter. Anyone whose lab stalled yesterday: this first block is the unblocking window — flag it now.

Today's arc is one sentence: a call is not an application. A script that works once on a good network, with a happy path and a human reading stdout, is a demo. An application is called by strangers, on flaky networks, with malformed inputs, at inconvenient volumes — and it must answer as structured data other code can parse. The morning gives you the four missing pieces — richer requests, structured outputs, streaming, failure handling — and the afternoon assembles them into a real service with a web face, built the way we said we would: spec first.

09:40 · Theory · part one

The SDK surface: three doors, one endpoint

Python code can reach your deployment through three SDK surfaces, and all three are thin layers over the same HTTPS endpoint — the choice is ergonomic, not architectural. azure-ai-inference is the one we use: a focused inference client (chat, embeddings, streaming) with first-class Entra ID support — small API, clean integration, our default. azure-ai-projects sits one level higher: it talks to the project (list deployments, open connections, later: agents and evaluations) and can hand you an inference client — the administrative surface around the calls. And the OpenAI-compatible surface: your endpoint also accepts the ubiquitous openai package pointed at your URL — valuable for porting existing code and examples, at the price of a less native identity story.

09:40 · Theory · part two

Anatomy of a chat completion

Everything you send is a list of messages, each with a role. system sets standing behaviour — persona, rules, format contracts; it speaks with the most authority and the user never sees it. user carries the human's turns; assistant carries the model's own previous answers. And here is the fact that shapes every chat application ever built: the model has no memory. Each call stands alone; "conversation" exists only because your code re-sends the relevant history every turn:

messages = [ … ] · what one multi-turn call actually sends
system · "You are Libra Assist…"
sent every single turn
user · "A customer's card is blocked…"
turn 1
assistant · "First, verify identity…"
the model's own turn 1 answer, echoed back
user · "And if verification fails?"
the new turn

Statelessness made visible: turn 2 re-sends turn 1. History grows linearly — and is re-billed every turn, which Session 1's context-window budget predicted.

Around the messages sit the parameters, each answering one production question:

ParameterWhat it controlsProduction stance
temperatureSampling sharpness: 0 ≈ deterministic, 1 ≈ variedLow for extraction/classification; moderate for prose
max_tokensHard cap on the completion lengthAlways set — it is your cost & latency ceiling
top_pNucleus sampling: restrict to the most probable massTune one of temperature/top_p, not both
stopSequences that end generation earlyHandy for delimited formats
response_formatFree text vs schema-conforming JSONThe structured-output mechanism — next block

And on the way back: choices[0].message (the answer), finish_reason ("stop" = model finished; "length" = your cap cut it off; "content_filter" = the gateway intervened), and the usage meter you already read by reflex.

10:05 · Live coding · 25′

Structured outputs, streaming & surviving failures

Three upgrades, live, each turning yesterday's script one notch more production-shaped.

1 · Structured output — JSON a program can trust

Free text is for humans; applications need fields. Asking nicely ("answer in JSON") works until it doesn't — the robust mechanism is response_format with a JSON schema, which constrains generation itself to the shape you declare:

structured.py 
from azure.ai.inference.models import JsonSchemaFormat

reply = client.complete(
    model="gpt-5.1",
    messages=[
        {"role": "system", "content": "Extract the transfer request from the user's message."},
        {"role": "user", "content": "Please send 2,500 lei to Maria Ionescu today, it's urgent."},
    ],
    response_format=JsonSchemaFormat(
        name="transfer_request",
        schema={
            "type": "object",
            "properties": {
                "beneficiary": {"type": "string"},
                "amount_ron":  {"type": "number"},
                "urgent":      {"type": "boolean"},
            },
            "required": ["beneficiary", "amount_ron", "urgent"],
            "additionalProperties": False,
        },
    ),
)
import json
data = json.loads(reply.choices[0].message.content)   # guaranteed to match the schema
print(data["beneficiary"], data["amount_ron"], data["urgent"])

Notice what changed philosophically: the prompt stopped being a wish and became an interface definition. This is the mechanism behind tool calling in Session 6 — an agent is, mechanically, a model emitting schema-conforming decisions.

2 · Streaming — perceived latency is a design choice

A 400-token answer takes seconds to generate but the first token arrives fast. Streaming renders tokens as they exist — the difference between an app that feels broken and one that feels alive. You saw the pattern in yesterday's stretch goal; today it goes into the product: the skeleton's chat endpoint streams.

3 · Failure is the normal case

On a shared quota, under real traffic, 429 Too Many Requests is not an accident — it is Tuesday. The engineering response is retry with exponential backoff: wait, double, try again, give up loudly after a budget:

robust_call.py 
import time
from azure.core.exceptions import HttpResponseError

def complete_with_retry(client, attempts=5, **kwargs):
    for attempt in range(attempts):
        try:
            return client.complete(**kwargs)
        except HttpResponseError as e:
            retriable = e.status_code in (429, 500, 503)
            if not retriable or attempt == attempts - 1:
                raise
            time.sleep(2 ** attempt)          # 1, 2, 4, 8 s — then give up loudly
FailureMeaningCorrect response
429Quota exceeded (TPM/RPM)Backoff and retry — never a tight loop
401 / 403Identity or role problemFail fast; fix auth — retrying cannot help
404Deployment name wrongFail fast; it's configuration
500 / 503 / timeoutTransient service/network faultRetry with backoff, bounded
finish_reason == "length"Your own cap truncated the answerHandle in logic — bigger cap or summarize
10:30 · Theory · 15′

Choosing a model: the quality · latency · cost triangle

"Which model?" is an engineering decision with three axes in permanent tension. Quality: task performance — but benchmark scores are screening evidence, not verdicts; only evaluation on your task (Session 4) settles it. Latency: time-to-first-token and tokens-per-second — a chat user feels both; a batch job feels neither. Cost: price per million tokens, input and output separately — multiplied by context length and traffic, which is why the meter habit exists. You cannot maximize all three; you choose which corner to sacrifice per workload.

Quality
task performance — proven by YOUR eval, not leaderboards
Latency
time-to-first-token · tokens/s
Cost
€ / million tokens, in + out

The selection triangle. Every workload picks a corner to sacrifice — pretending otherwise just picks one at random.

Model classTradeReach for it when
Flagship chat (our gpt-5.1)High quality, moderate latency & costCustomer-facing language, complex instructions — Libra Assist's voice
Small / mini modelsFraction of the cost & latency, lower ceilingClassification, routing, extraction at volume — most calls in mature systems
Reasoning modelsDeliberate longer for hard problems — slow, costlyMulti-step analysis where wrong is expensive; never for chit-chat
Embedding modelsNo generation at all; cents at scaleSearch and retrieval — Session 5's engine

Two production patterns to know by name: the router (a cheap model classifies each request and forwards only the hard ones to the expensive model) and the fallback chain (primary deployment fails or throttles → secondary answers). Both are just the triangle, applied per request instead of per product — and both become trivial to build once model access is behind one gateway.

10:55 · Walkthrough · 30′

The skeleton, built spec-first with an AI agent

Yesterday's closing theory becomes practice. I have an idea — "a local web chat talking to our deployment" — and instead of typing it, I wrote it down. This is the entire specification; read it as a contract:

SPEC.md · Libra Assist skeleton, v0 
# Libra Assist — starter skeleton (v0)

Goal      : a local web chat talking to our Foundry deployment.

Backend   : Python 3.11+, FastAPI
  POST /chat      {message, history}  ->  {reply, usage}
  GET  /          serves the chat page (static)
Frontend  : ONE html file, no framework — input box, message list,
            token counter under every answer
Model     : gpt-5.1 via azure-ai-inference, keyless (DefaultAzureCredential)
Config    : endpoint from env var AZURE_AI_ENDPOINT — never hardcoded
Behaviour : system prompt = Libra Assist banking persona; history sent
            each turn (the API stays stateless); errors surface as
            readable messages, 429 retried with backoff
Non-goals : no database, no retrieval, no login, no deployment
            (each arrives in a later session)

Watch the loop run for real: the agent reads the spec, proposes a plan (file layout, endpoints, order of work) — we review the plan before any code exists — then it implements, and we verify the result against the spec, point by point, before committing. Conclusions

What today changed

The model became a dependency. You now compose requests deliberately — roles, history, parameters — and you know the model remembers nothing unless your code re-sends it. You can demand structured JSON and get it by schema, not by luck; you treat 429 as weather, not catastrophe; and you place workloads on the quality–latency–cost triangle like someone who will be asked to defend the bill. Above all: Libra Assist is no longer a script. It is an application with a spec, a repository, an API and a face — built by an AI agent under review, running on your machine. On Monday we stop admiring its answers and start measuring them.

Takeaways

If you remember six things

1. The model is stateless — "conversation" is your code re-sending history, and re-paying for it, every turn.

2. Structured output by schema turns a prompt into an interface — the foundation tool calling stands on.

3. 429 is normal. Exponential backoff is the polite, professional answer; a tight retry loop is a self-inflicted outage.

4. finish_reason tells you why generation ended — "length" means you cut the model off, and code must care.

5. Quality, latency, cost — pick which to sacrifice per workload; routers and fallbacks are that choice made per request.

6. Spec → plan → implement → verify. The agent types; you own intent, review and judgment.
