# Assignment 1 — Run the RAG backend, then build its admin console

**Module:** AI Engineering on Azure · Libra Bank Academy
**Estimated effort:** 3–5 hours · **Difficulty:** foundational
**Due:** before our next session — confirm the exact date on the module calendar.

This assignment has two halves. First you get the course backend — the **RAG
Teaching API** — running on your own machine against **Azure AI Foundry**. Then you
build a small **admin console** on top of it. That console is not throwaway: it
becomes the operator/admin surface of the app we build across the module, **Libra
Assist**.

---

## Why this assignment

Everything later in the course (prompting, evaluation, retrieval, orchestration)
is exercised through this backend. If it runs cleanly on your laptop and you
understand the shape of its endpoints, every following session is hands-on instead
of spent fighting setup. Building the admin UI forces you to actually read the API
contract — request bodies, responses, status codes — which is the real learning.

## Learning outcomes

By the end you will be able to:

- Run a containerised FastAPI + vector-database stack locally with Docker Compose.
- Configure an app to call Azure AI Foundry, and explain the difference between the
  **keyless (identity)** and **key** authentication lanes — and when each applies.
- Read and exercise a REST API from both Swagger and Postman.
- Build a thin frontend that consumes a documented API and surfaces its results and
  errors honestly.

## Part 1 — Get the backend running

The backend is the **RAG Teaching API** in [`code/backend/`](../../code/backend).
It is a FastAPI app (port **7799**) plus a **Qdrant** vector database (port
**7833**), both orchestrated by Docker Compose. The full reference is its own
[README](../../code/backend/README.md) — this is the short path.

Do the steps **in order** — in particular, create `.env` *before* you start the
stack, because Compose reads it at launch and will refuse to start without it.

### 1. Install and start Docker

Install Docker Desktop and launch it. Confirm it works:

```bash
docker --version
docker compose version
```

Both should print a version, and Docker Desktop should show the engine as
**running**.

### 2. Open the backend folder

From the repository root (pull the latest first if you already have the repo):

```bash
cd code/backend
```

### 3. Create your `.env` from the template

```bash
cp .env.example .env
```

On Windows PowerShell use `Copy-Item .env.example .env` instead. This gives you a
fully commented config file; you only need to fill in the Foundry section.

### 4. Add your Foundry credentials to `.env`

Open `.env` and set these values:

```ini
AZURE_AI_ENDPOINT=https://<your-resource>.services.ai.azure.com/models
AZURE_AI_CHAT_DEPLOYMENT=gpt-5.1
AZURE_AI_EMBEDDING_DEPLOYMENT=text-embedding-3-small

# We run inside Docker, so use KEY auth (see the note below):
AZURE_AI_AUTH=key
AZURE_AI_API_KEY=<paste Key 1 from the Foundry portal>
```

Get the endpoint and key from the Foundry portal → your project/resource →
**Keys and Endpoint** (`docs/topics/ref-foundry.html` shows exactly where).

> **Why key auth and not keyless?** The template ships with `AZURE_AI_AUTH=identity`,
> which is the recommended lane when you run the app **directly on your machine**
> (`az login` provides your identity). But we are running the API **inside a
> container**, and `az login` does not exist there — so inside Docker you must use
> `AZURE_AI_AUTH=key`. This is the single most common thing that trips people up.

**Never commit `.env`.** It holds a secret and is already git-ignored — that is the
whole reason the key lives there and not in code.

### 5. Start the stack

```bash
docker compose up -d --build
```

`-d` runs it in the background; `--build` builds the API image (needed the first
time and after code changes). This starts two containers: `rag-api` (the FastAPI
app, port 7799) and `rag-qdrant` (the vector DB, port 7833). The first run pulls
images and may take a few minutes.

Useful companion commands:

```bash
docker compose ps          # are both containers up?
docker compose logs -f api # follow the API logs (Ctrl-C to stop following)
docker compose down        # stop and remove the containers when you're done
```

### 6. Verify it's alive — Part 1 acceptance

Check all three:

- **Swagger UI:** <http://localhost:7799/docs> — the interactive API surface.
- **Health:** <http://localhost:7799/health> — the JSON should read `status: "ok"`,
  `qdrant: "ok"`, and show `azure` as the chat and embedding provider.
- **Qdrant dashboard:** <http://localhost:7833/dashboard> — the database's own UI.

> **Part 1 is done when** `GET /health` returns `ok` with Qdrant reachable and the
> Azure providers listed. If it doesn't, jump to [Troubleshooting](#troubleshooting)
> before moving on.

## Part 2 — Drive the API by hand

Before you wrap a UI around the API, use it directly so you understand what each
call does. Use **Swagger** (`/docs`, "Try it out" on each endpoint) or import the
**Postman** collection at
[`postman/rag-teaching-api.postman_collection.json`](../../code/backend/postman/rag-teaching-api.postman_collection.json).

Walk the retrieval pipeline in this order and *read the responses*:

| Step | Call | What to notice |
|---|---|---|
| 1 | `GET /health`, `GET /config` | What's configured and reachable |
| 2 | `POST /chunk` | Same text, four `strategy` values → different boundaries |
| 3 | `POST /ingest` | Chunks become vectors — note the dimension |
| 4 | `GET /collection` | What Qdrant now holds |
| 5 | `POST /search` | A paraphrased query still finds the right chunk (cosine scores) |
| 6 | `POST /ask` with `use_rag: false` then `true` | Compare the answers **and** the `prompt_sent` — that difference *is* RAG |
| 7 | `DELETE /collection` | Clean slate |

This is the exact surface your admin console will wrap, so make sure each response
makes sense to you.

## Part 3 — Build the admin console (the deliverable)

Build a **simple frontend** that talks to the running backend at
`http://localhost:7799`. Think of it as the **admin panel of Libra Assist**: the
screen an operator uses to load knowledge, inspect what's stored, and test answers —
not the end-user chat.

**Tech is your choice.** Plain HTML + CSS + JavaScript (`fetch`) is completely
acceptable and probably fastest; a small React/Vue app is fine too. Favour clarity
over polish.

### Minimum requirements (must-have)

A UI that lets an admin do all of the following, each wired to the matching endpoint:

1. **Service status** — call `/health` (and `/config`); show the active
   providers/models and whether Qdrant is up.
2. **Chunk** — `POST /chunk`; let the user paste text, pick a `strategy`
   (`static` / `sentence` / `dynamic` / `semantic`), and see the resulting chunks.
3. **Ingest** — `POST /ingest`; show how many chunks were stored and the vector
   dimension.
4. **Collection** — `GET /collection` to show what's stored, and `DELETE
   /collection` to reset it (guard this with a confirm).
5. **Search** — `POST /search`; show the returned chunks **with their similarity
   scores**, highest first.
6. **Ask** — `POST /ask`; let the user type a question, toggle `use_rag`, and
   display the **answer**, the **retrieved chunks**, and the **`prompt_sent`**.

Surface **errors honestly**: the API returns meaningful status codes and messages
(e.g. `409` on a dimension mismatch, `503` when Qdrant is down) — show them to the
user instead of failing silently.

### Constraints

- Talk **only** to the local API. CORS is already open (`*`), so a static page
  served from disk or a dev server can call it directly.
- **No secrets in the frontend.** The Foundry key stays server-side in `.env`; the
  browser never sees it.
- You may use the course palette/tokens (see [`resources/ui-kit.md`](../../resources/ui-kit.md)),
  but a clean unstyled tool is fine.

### Stretch goals (optional)

- Show the first few numbers of an embedding vector returned by `/ingest`/`/search`.
- Let the user compare `use_rag: false` vs `true` side by side for the same question.
- Persist the last-used settings (strategy, `top_k`) in `localStorage`.

### Part 3 acceptance criteria

Accepted when a reviewer can, **from your UI alone**, run the full
`/chunk → /ingest → /search → /ask` flow against a running backend, see the
similarity scores, and read the `prompt_sent` for a RAG answer.

## Troubleshooting

First stops for the usual issues (the backend README has the
[full table](../../code/backend/README.md#troubleshooting)):

| Symptom | Fix |
|---|---|
| Compose won't start: "env file .env not found" | You skipped step 3 — `cp .env.example .env` first |
| `503 Qdrant is not reachable` | Qdrant container isn't up — `docker compose ps`, then `docker compose up -d` |
| `502 … 401` on `/ask` or `/ingest` | Wrong or expired key, or wrong endpoint — recheck the Foundry values in `.env` |
| Works when run locally, fails in Docker | You're on identity auth in a container — set `AZURE_AI_AUTH=key` + `AZURE_AI_API_KEY` |
| `409` on `/ingest` | You changed embedding models — `DELETE /collection`, then ingest again |
| Port already in use | Change `API_PORT` and/or the Compose port mappings |

After editing `.env`, restart so it's picked up: `docker compose up -d`.
