---

## Why this assignment

A RAG system is easy to make *work* and hard to make *good*. The gap between the two is
almost entirely in three places: **the data you put in**, **how you cut it up**, and
**what you retrieve**. The model is the part you change least.

So this assignment gives you a corpus you invented — which means you know the right
answers — and asks you to make the assistant answer well against it. When something is
wrong you will be able to say *why*: the chunk was cut badly, the score was too low, the
question needed two documents, the answer was not in the corpus at all. That diagnosis
is the skill; the code is the easy part.

## Learning outcomes

By the end you will be able to:

- Fork a repository, keep your fork in sync with upstream, and work without fear of
  either losing your work or diverging silently.
- Design a document corpus deliberately, including the cases that break naive retrieval.
- Change chunking and retrieval, and *measure* whether the change helped.
- Tell apart questions a single lookup can answer from those that need several steps —
  and explain which parts of your assistant handle which.

## Part 2 — Fork the repository

Until now you had a **clone**: a copy on your machine, pushing back to the course repo
(which you cannot). A **fork** is a copy *on GitHub, under your account* — you own it,
you push to it, and it remembers where it came from so you can still pull our updates.

### 1. Create the fork

1. Open the course repository on GitHub:
   <https://github.com/luciangruiaro/ai-acad-foundry-2026>
2. Click **Fork**, top right.
3. On the next screen: keep the name, leave *"Copy the `main` branch only"* **ticked**,
   and click **Create fork**.
4. After a few seconds you land on `https://github.com/<your-username>/ai-acad-foundry-2026`
   — note it says *"forked from luciangruiaro/ai-acad-foundry-2026"* under the title.

### 2. Point your local repository at your fork

You already have the code locally, so **do not clone again**. Rename the remotes so the
names say what they mean — `origin` = yours, `upstream` = ours:

```bash
cd <your local repo>

git remote rename origin upstream
git remote add origin https://github.com/<your-username>/ai-acad-foundry-2026.git
git remote -v
```

Expect exactly this shape:

```
origin    https://github.com/<your-username>/ai-acad-foundry-2026.git (fetch)
origin    https://github.com/<your-username>/ai-acad-foundry-2026.git (push)
upstream  https://github.com/luciangruiaro/ai-acad-foundry-2026.git (fetch)
upstream  https://github.com/luciangruiaro/ai-acad-foundry-2026.git (push)
```

Now push what you have to your fork:

```bash
git switch main
git push -u origin main
```

> **Starting clean instead?** `git clone https://github.com/<your-username>/ai-acad-foundry-2026.git`
> then `git remote add upstream https://github.com/luciangruiaro/ai-acad-foundry-2026.git`.
> Same end state.

### 3. Make a branch for your project

```bash
git switch -c project
git push -u origin project
```

Work here. Keep `main` as a clean mirror of ours — that is what makes step 4 painless.

### 4. Pulling our updates later

The course repo keeps moving. Whenever you want the new material:

```bash
git switch main
git fetch upstream
git merge upstream/main        # main now matches ours again
git push origin main           # keep your fork's main in step too

git switch project
git merge main                 # bring the updates into your work
```

Conflicts here are normal and mean you changed the same lines we did — resolve, `git add`,
`git commit`. To back out: `git merge --abort`. The merge-vs-rebase reasoning is in
[How git works](../topics/ref-git.html#merging).

### Part 2 acceptance

`git remote -v` shows `origin` = your fork and `upstream` = ours; your `project` branch
exists on GitHub; and `git fetch upstream` succeeds.

## Part 3 — Fabricate your corpus

Invent a small **banking knowledge base**. Fiction is required, not tolerated: never use
real customer data, and do not paste your employer's internal documents.

Pick a domain narrow enough to be coherent — cards, mortgages, deposits, onboarding,
fees, complaints — and write **12–25 documents**, a few hundred words each, in
`data/` on your branch (Markdown or plain text).

### Write these cases in on purpose

Your corpus should be able to *break* a naive pipeline. Include at least one of each:

| Case | Why it matters | Example |
|---|---|---|
| **A precise number** | Vector search is vague about exact tokens | "the early repayment fee is 1%" |
| **Two documents that must be combined** | Tests whether one chunk is ever enough | eligibility in one file, the fee schedule in another |
| **Near-duplicates that differ** | Retrieval must return the *right* one | the 2025 fee list and the 2026 fee list |
| **A long procedure with steps** | Chunking will try to cut it in half | card replacement, step by step |
| **A table** | Plain-text chunking mangles these | fees per account type |
| **Contradiction across versions** | Forces you to think about metadata and dates | a limit that changed in January |
| **Something deliberately absent** | The assistant must refuse, not invent | student loans, which your bank does not offer |

Give every document a small header — title, effective date, audience, product — because
Part 4 turns that into metadata, and metadata is what makes filtering possible.

```markdown
---
title: Card blocking and unblocking
product: cards
audience: retail
effective: 2026-01-15
version: 3
---

A card is blocked automatically after three failed PIN attempts...
```

### Part 3 acceptance

`data/` on your branch holds 12–25 documents, each with a header, covering at least five
of the seven cases above. A `data/README.md` says what the corpus is and lists which
document covers which case.

## Part 4 — Ingest it, and improve the ingestion

Get it in first, then make it better.

```bash
curl -X POST http://localhost:7799/ingest -H "Content-Type: application/json" -d '{
  "text": "<one document>", "strategy": "dynamic", "source": "cards-policy"
}'
```

Doing that 20 times by hand is the point at which you write a loader — a small script
that walks `data/`, reads each file, and posts it with a sensible `source`. Put it in
`code/backend/scripts/` and commit it.

### Then pick at least two real improvements

Each of these is a genuine weakness of the current implementation, not a made-up
exercise. The files to look at are named.

| # | Improvement | Where | Why it matters |
|---|---|---|---|
| 1 | **Stable chunk ids** — re-ingesting a document currently *duplicates* it, because every chunk gets a fresh UUID | `app/vectorstore.py` → `upsert()` | Derive the id from source + index (or a content hash) so re-ingesting replaces instead of piling up |
| 2 | **Real metadata** — store title, product, effective date, version in the payload | `app/vectorstore.py`, your loader | Nothing can be filtered by what was never stored |
| 3 | **Heading-aware chunking** — a new strategy that splits on Markdown headings and keeps the heading with its text | `app/chunking.py` | Your documents *have* structure; the current strategies ignore it |
| 4 | **Never split a table or a numbered list** | `app/chunking.py` | Where naive chunking damages meaning most visibly |
| 5 | **Chunk context** — prefix each chunk with its document title and section | your loader or `chunking.py` | A chunk retrieved alone often lacks the noun it refers to |
| 6 | **Per-document collections or a `source` filter** | `app/vectorstore.py` | Lets you re-ingest one document without wiping everything |

Measure the effect. Before and after, run the same three questions and write down the
scores — an improvement you cannot demonstrate is an opinion.

### Part 4 acceptance

A loader script ingests your whole corpus in one command; at least two improvements are
implemented; and `NOTES.md` records one before/after comparison with real numbers.

## Part 5 — Improve retrieval

The current `/search` embeds the query and returns the top *k* by cosine similarity.
That is the honest minimum. Pick **at least two**:

| # | Improvement | Where | The problem it solves |
|---|---|---|---|
| 1 | **A score threshold** — drop hits below a floor and say "nothing relevant found" | `app/main.py` → `/search`, `/ask` | Retrieval always returns *something*; weak hits become confident wrong answers |
| 2 | **Metadata filters** — restrict by product, audience or effective date | `app/vectorstore.py` → `search()` | The 2025 fee list stops competing with the 2026 one |
| 3 | **Keyword + vector (hybrid)** — combine exact matching with semantic | `app/vectorstore.py` | Account numbers, product codes and IBANs, which vectors handle badly |
| 4 | **Query rewriting** — one cheap model call turns a messy question into a better query | `app/rag.py` or a new module | "it got blocked again??" is a poor embedding input |
| 5 | **Deduplication / diversity** — avoid three chunks that say the same thing | `app/vectorstore.py` | Wastes context budget and hides the second fact |
| 6 | **Re-ranking** — retrieve 10, ask the model to pick the best 3 | new module, called from `/ask` | Cosine ordering is blunt; a model reading the text is not |

> Qdrant supports payload filters and full-text indexes natively — the
> [Qdrant filtering docs](https://qdrant.tech/documentation/concepts/filtering/) cover
> #2 and #3. Azure AI Search does all of this as a managed service, which is the
> comparison in [Session 4 → Retrieval](../sessions/s04-foundry-in-practice.html#ai-search);
> implementing one by hand first is how you understand what it is doing for you.

### Part 5 acceptance

At least two retrieval improvements, each with a sentence in `NOTES.md` saying what it
fixed and one question that demonstrates it.

## Part 6 — Design your question set

Write **15 questions** in `data/questions.md`, and for each record the expected answer
and which documents contain it. This is the beginning of an evaluation set — the thing
Session 5 turns into measurement.

Sort them into three groups:

**A · Simple retrieval (about 7)** — the answer sits in one chunk of one document.
*"What is the fee for early repayment during the fixed-rate period?"*

**B · Multi-step (about 5)** — the answer needs more than one lookup, a comparison, or a
small calculation.
*"I have a fixed-rate mortgage of 200,000 lei and want to repay 50,000 early — what will
it cost me, and does that change if I wait until the variable period?"*
Note what makes it hard: two documents, or retrieval then arithmetic, or a condition to
check first.

**C · Must refuse (about 3)** — the answer is genuinely not in your corpus, or the
question is out of scope.
*"What is the interest rate on your student loans?"* (your bank does not offer them)
A confident invented answer here is a **failure**, and catching it is the point.

Then run all 15 through your assistant and record what happened: correct, wrong, refused
correctly, refused when it should have answered. Be honest — a mediocre score you
understand is worth more than a good score you cannot explain.

> **About "agentic":** group B is where a single retrieval stops being enough. Today your
> assistant handles those by retrieving more and reasoning in one call. In **Session 6**
> we give the agent *tools* — so it can decide to search again, call a function, or look
> something up — and these are the questions you will use to show the difference. Design
> them now so the comparison is real.

### Part 6 acceptance

`data/questions.md` holds 15 questions in three labelled groups, each with an expected
answer, the source documents, and what your assistant actually answered.

## Part 7 — Your frontend

Libra Assist needs a face. **Two starting points — both fine, choose deliberately:**

| Start from | When it fits | How |
|---|---|---|
| **The course console** (`code/frontend/`) | You want the pipeline views — chunking, scores, prompts — and to focus your effort on the conversation | It is already in your fork. Change it; it is yours now |
| **Your Assignment 1 admin console** | You would rather grow what you built and understand every line | Bring it into your fork under `code/frontend/` (or beside it) and continue |

Either way, the target is **a conversational Libra Assist** — not an API explorer:

**Must have**
1. A **chat** interface with visible conversation history.
2. The **agent/persona** selectable, so a reviewer can see behaviour change.
3. **Sources shown** for grounded answers — which documents were used, with scores.
4. **Honest failure**: when the assistant refuses or retrieval finds nothing, say so
   plainly rather than showing a blank.

**Worth adding**
- A toggle for `use_rag`, so you can demonstrate the difference live.
- Token usage per answer — the cost habit from Session 2.
- An ingestion screen, so you can add a document without curl.
- Your own visual identity. The [UI kit](../../resources/ui-kit.md) is available, and
  ignoring it entirely is a legitimate choice.

> The backend keeps no conversation state — `/ask` is stateless. Multi-turn chat is
> therefore *your* frontend's job for now: keep the history and decide what to send.
> That constraint is deliberate, and Session 5 revisits it when we add persistence.

### Part 7 acceptance

From your frontend alone, a reviewer can hold a multi-turn conversation with Libra
Assist, switch persona, see which documents grounded an answer, and watch it refuse a
question from group C.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `git push` rejected: permission denied | You are pushing to `upstream`. Check `git remote -v` — pushes go to `origin`, your fork |
| Ingesting the same document twice doubles the hits | Expected today — that is improvement #1 in Part 4 |
| Every search returns the same chunk | `top_k` too low, or one document dominates. Try a filter, or improvement #5 |
| Answers cite the wrong version of a document | You need metadata and filters — improvements #2 and #2 |
| The assistant invents an answer to a group C question | Check `refuse_when_unsupported` in your persona, and add a score threshold |
| `409` on ingest | Embedding model changed — `DELETE /collection`, then re-ingest |
| Merge conflicts after `git merge upstream/main` | Normal. Resolve, `git add`, `git commit`; or `git merge --abort` and ask |
