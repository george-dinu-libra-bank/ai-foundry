Microsoft Foundry — the platform, step by step

From an empty Azure account to a deployed language model answering calls from your own machine.

What Microsoft Foundry is and how it's organized; a click-by-click tutorial that takes a brand-new Azure account to working chat and embedding deployments; how to call them from a local Python application — including the honest answer to "do I need an API key, the Azure CLI, or PowerShell?"; how to watch your consumption; and how all of this compares to calling OpenAI directly.

The platform

What Microsoft Foundry is

Microsoft Foundry is Microsoft's unified platform for building applications on top of AI models: a model catalog spanning many providers, managed deployments that expose those models as authenticated HTTPS endpoints, project workspaces with access control, an agent runtime, evaluation tooling, and observability — one resource in your Azure subscription instead of a dozen separately wired services. Conceptually it is a platform-as-a-service for inference: you never see the GPUs, the model weights or the serving infrastructure; you see an endpoint, a quota and a bill.

The name is the newest layer of a decade of consolidation, and you will meet every older name in documentation and in real estates:

One product line, five names. Reading older tutorials is fine — the concepts map one-to-one.

Foundry presents two faces over the same objects. In the Azure portal (portal.azure.com) it is infrastructure: a resource in a resource group, with networking, identity, cost and policy — the governance lens. In the Foundry portal (ai.azure.com) it is a workbench: projects, model catalog, playground, agents, evaluations — the builder lens. Everything in this page's tutorial uses both, in that order.

Hands-on · tutorial

From an empty Azure account to a deployed model

This walkthrough assumes exactly one thing: a fresh Azure account — a company-provided one or a personal free account (which includes a time-limited credit and a set of always-free services). Every step is in the portal; no command line needed until your first API call. The path you are about to walk:

Seven steps, ~15 minutes on a quiet day. Each numbered step below is one arrow.

Step 1 — verify your subscription

Sign in at portal.azure.com. Search for Subscriptions in the top bar and confirm one exists (free accounts get one automatically). The subscription is the billing and quota boundary — everything you create below hangs from it.

Step 2 — create a resource group

Search Resource groups → Create. Choose your subscription, name it (e.g. rg-ai-course), and pick a region close to you that offers AI services broadly — for Europe, West Europe or Sweden Central are safe defaults. The group is the lifecycle unit: deleting it later removes everything in it, which is exactly what you want for a learning setup.

Step 3 — create the Foundry resource

Search Microsoft Foundry → + Create → choose "Foundry (Recommended)" (not "Azure OpenAI" — you want the platform, not the single-family lane). Select subscription, your resource group, region, and a globally unique name (it becomes part of your endpoint URL, e.g. my-foundry-lb → my-foundry-lb.services.ai.azure.com). Review + create → Create, and wait for deployment to finish. Creation also provisions your first project.

Step 4 — open the Foundry portal

From the resource's overview click Go to Foundry portal (or visit ai.azure.com and sign in with the same account). Select your project and orient yourself: Overview shows the project's endpoint and API keys; Models + endpoints lists deployments (empty for now); the Model catalog is where the next step happens.

Step 5 — deploy a chat model

Open the Model catalog, find your chat model (in this course: gpt-5.1), and click Deploy. Three decisions appear: the deployment name (the string your code will reference — keeping it equal to the model name is a sane convention), the deployment type (start with a standard/global pay-as-you-go type; see the next section for what the options mean), and the tokens-per-minute quota allocation. Confirm, and in under a minute the model is an endpoint with a name.

If Deploy is greyed out or a model is missing

That is quota or regional availability, not a mistake on your part. Not every model exists in every region, and fresh trial subscriptions get modest default quotas with some families requiring a quota request. Check the model's region list, or create the resource in a better-served region.

Step 6 — deploy the embedding model

Repeat step 5 for text-embedding-3-small. Two deployments — one generative, one embedding — are the complete model estate this course needs until its final session.

Step 7 — prove it in the playground

Open the playground, select your chat deployment, set a system prompt ("You are a precise banking assistant…"), ask a question, and adjust temperature to see its effect. The playground is the zero-code sanity check: if it answers here, the platform side is done and every remaining problem is on the client side — which is precisely the next section.

Hands-on

Choosing models in the catalog

The catalog lists thousands of entries — OpenAI models alongside Meta, Mistral, DeepSeek, xAI and open-weight families — so choosing is a filtering discipline, not a browsing one. Filter by task first (chat completion vs embeddings vs image), then compare candidates on four axes: capability (benchmark scores and leaderboards are in the catalog — treat them as screening evidence, not verdicts; your own evaluation in Session 4 is the verdict), context window (how much input it can attend to), latency class (reasoning models deliberate longer), and price per million tokens, input and output priced separately.

Orthogonal to which model is how it is served — the deployment type, which sets your traffic contract:

Deployment typeServingBillingChoose when…
Global standardRouted across Microsoft's global fleetPay per tokenDefault for development and most production — best availability
Standard (regional)Served within the resource's regionPay per tokenData-processing residency requirements pin traffic to a region
Provisioned (PTU)Reserved throughput capacityCapacity units per hourSustained high traffic needing guaranteed throughput and stable latency

Every pay-per-token deployment carries a tokens-per-minute (TPM) and requests-per-minute quota; exceeding them yields HTTP 429 responses — which is why resilience and retry logic are a Session 3 topic rather than an afterthought.

For embedding models the decision is simpler but stickier: capability matters (retrieval-quality benchmarks), dimensionality trades quality against storage and compute per comparison (1536 for text-embedding-3-small, 3072 for its larger sibling), price per million tokens is far below chat models — and above all, the choice is a commitment: vectors from different models are not comparable, so re-choosing later means re-embedding the entire corpus. Multilingual quality matters in a Romanian bank; verify it on your own text before committing.

Hands-on

Calling your deployment from a local application

A deployment is an HTTPS endpoint; any HTTP client can call it. What varies is how the call authenticates, and this is where the perennial question lands: "do I need an API key? the Azure CLI? PowerShell?" The precise answer: there are two authentication lanes, and your tooling needs depend on which one you take.

Lane A · API key
Copy key + endpoint
project Overview page
App sends key with each request
Needs: nothing else installed
works anywhere, instantly
Lane B · Microsoft Entra ID (keyless)
Developer signs in once
az login / Connect-AzAccount / VS Code
DefaultAzureCredential picks up the session,
exchanges it for a short-lived token
Needs: Azure CLI or Az PowerShell
+ an RBAC role on the resource

Two lanes to the same endpoint. Key = fastest to start, weakest to operate. Entra ID = one-time setup, then no secrets exist to leak.

So, concretely: with an API key you need neither the Azure CLI nor PowerShell — the key and endpoint are sufficient. For keyless (Entra ID) authentication from a local machine you need one sign-in source installed: the Azure CLI (az login) is the usual choice; Azure PowerShell (Connect-AzAccount) or VS Code's Azure sign-in work equally well. DefaultAzureCredential probes those sources in a fixed order and uses the first that responds — the same code later runs unchanged in the cloud, where a managed identity satisfies the chain instead:

→
Managed identity
in Azure, later
→

→

az login — our lab path
→
Azure PowerShell

DefaultAzureCredential's probe order (simplified): first source that yields a token wins. Locally that's your CLI login; in the cloud, the managed identity.

Keyless has one more prerequisite: authorization. Your identity needs a data-plane RBAC role on the Foundry resource — Cognitive Services User (or the newer Azure AI User) is the canonical read-and-call role. Owners of a fresh personal subscription have it implicitly; in an organization it must be assigned. With that in place, the code:

setup, once 
pip install azure-ai-inference azure-identity
az login                      # opens a browser; signs your machine in
chat_keyless.py · Lane B (recommended) 
from azure.ai.inference import ChatCompletionsClient
from azure.identity import DefaultAzureCredential

ENDPOINT = "https://<your-resource>.services.ai.azure.com/models"

client = ChatCompletionsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())
reply = client.complete(
    model="gpt-5.1",          # your DEPLOYMENT name
    messages=[{"role": "user", "content": "One sentence: what is Microsoft Foundry?"}],
)
print(reply.choices[0].message.content)
print(reply.usage)            # prompt_tokens / completion_tokens — your cost, per call
embeddings_keyless.py 
from azure.ai.inference import EmbeddingsClient
from azure.identity import DefaultAzureCredential

client = EmbeddingsClient(endpoint=ENDPOINT, credential=DefaultAzureCredential())
result = client.embed(model="text-embedding-3-small",
                      input=["my card is blocked", "frozen debit card"])
print(len(result.data[0].embedding))   # 1536 dimensions

The key-based variant differs in one line — and in its operational consequences. Keys are two per resource, long-lived, rotatable, and grant full data-plane access to whoever holds them; if you must use one (quick demos, tooling that supports nothing else), load it from an environment variable, never from source code:

chat_with_key.py · Lane A (know it; avoid it) 
import os
from azure.ai.inference import ChatCompletionsClient
from azure.core.credentials import AzureKeyCredential

client = ChatCompletionsClient(
    endpoint=ENDPOINT,
    credential=AzureKeyCredential(os.environ["FOUNDRY_API_KEY"]),  # from env, never hardcoded
)

Why this course never ships a key

A leaked key is an unattributed, unexpiring grant of your quota and your bill — and git history never forgets. Banks ban long-lived secrets in code for exactly this reason. Lane B costs you one az login and removes the entire failure class; it is the only lane our labs use.

One compatibility note that saves confusion: Foundry endpoints also speak the OpenAI SDK dialect — the openai Python package can target your deployment by pointing its base URL at your endpoint. Useful when porting code written for OpenAI; our labs stay on azure-ai-inference for the clean Entra integration. The full request path, whichever SDK you choose:

Hands-on

Monitoring resources & consumption

A metered platform must be watched from day one — not because disaster is likely, but because consumption is a system metric exactly like latency. Foundry consumption has three observation points, each answering different questions at different freshness:

Your app's calls
→
Deployment
per-response usage object
exact, immediate, per call
metrics → Azure Monitor
requests, tokens, latency — minutes
costs → Cost Management
money, by resource/tag — hours to a day

Three telemetry streams off every deployment: exact per-call usage in the response, operational metrics in Monitor, money in Cost Management.

QuestionWhere to answer it
What did this call cost?The usage object on the response: prompt_tokens, completion_tokens. Exact and immediate — this is what our labs log to SQL in Session 5.
How busy is the deployment?Foundry portal → your project → Models + endpoints → deployment metrics; or Azure portal → resource → Metrics: requests, processed tokens, time-to-first-token, 429 rate.
Am I about to hit limits?The quota view (Foundry portal, Management/Quota) — TPM allocated vs consumed per model and region; 429 responses are the symptom of crossing it.
What does the month cost, in money?Azure portal → Cost Management → cost analysis, filtered to the resource group or tags. Token prices differ per model and direction (input vs output), so cost ≠ call count.
Why was that answer slow / wrong?Tracing: Foundry's observability integrates with Application Insights — per-request traces across your app and its model calls. We wire this in Session 6.

Set a budget before you need one

Cost Management lets you define a monthly budget with e-mail alerts at thresholds (50%, 90%, 100%). On any experimentation subscription this is the first thing to configure — it converts a surprise invoice into a Tuesday e-mail.

Perspective

Foundry vs taking the model directly from OpenAI

The same GPT model is reachable two ways: directly from OpenAI (api.openai.com, OpenAI's contract, OpenAI's infrastructure) or through your Foundry deployment (your Azure tenant, Microsoft's contract, your region). The model weights are the same; almost everything around them differs — and the difference is precisely the boundary your traffic crosses:

Same model, different boundary. For a bank, the right-hand frame is usually the entire argument.

DimensionOpenAI directThrough Microsoft Foundry
Contract & data handlingOpenAI's terms; API data not used for training by default; processed in OpenAI's infrastructureMicrosoft's enterprise terms under your existing Azure agreement; prompts/completions stay within Azure's boundary, not shared with OpenAI the company
Residency & regionLimited control over processing locationYou pick the region (regional deployment types); aligns with data-residency obligations
Identity & accessAPI keys (org/project scoped)Entra ID: RBAC, managed identities, conditional access — no standing secrets
NetworkingPublic endpointPublic or fully private (Private Link/VNet) — traffic never touches the public internet if so configured
Compliance surfaceOpenAI's certification setAzure's certification portfolio + your negotiated DPA; audits inherit your Azure posture
Throughput guaranteesRate limits by pricing tierQuotas you manage; provisioned throughput (PTU) for reserved capacity and SLA-backed latency
Model availabilityNew OpenAI features/models land here firstTypically shortly after — plus the multi-vendor catalog OpenAI cannot offer
Platform around the modelModel API + assistants toolingProjects, Agent Service, evaluations, tracing, content filters, one Azure bill

The honest guidance follows from the table rather than from loyalty. Direct OpenAI is a fine choice for personal prototypes, consumer-facing products without residency constraints, and for touching brand-new capabilities on launch day. Foundry is the default in an enterprise — and effectively mandatory in a regulated one: identity-based access instead of shared secrets, region pinning, private networking, provisioned capacity, and audit through the same governance the rest of the estate already passes. That is why "which models are we using, and through what?" is a governance question a bank tracks — and why this course runs every call through Foundry.
