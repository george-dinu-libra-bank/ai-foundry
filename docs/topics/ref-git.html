How git works

Version control from first principles — the model in your head, then the commands in your hands.

Git is the version-control system behind essentially all modern software work, including this course: the starter application arrives as a git repository, and every lab builds on it. Git is famously confusing when learned as a list of commands and famously simple once you know the model underneath. This page teaches the model first.

Reference page ~15 min read Used from Session 3 onward
The model

Why version control exists

Software is text that changes constantly, usually at the hands of several people at once. Without tooling, that reality degenerates fast — files named final_v2_REALLY_FINAL.py, changes overwriting each other, no way to answer "what did we change, when, and why?", and no safe path back when something breaks. A version control system (VCS) solves this by making history a first-class object: every meaningful state of the project is recorded as a commit — who changed what, when, and (via the commit message) why — and any recorded state can be revisited, compared or restored at will.

Version control also unlocks parallel work. Two people — or you and an AI coding agent — can change the same project simultaneously on separate branches and merge the results deliberately, with conflicts surfaced explicitly instead of silently lost. In this course you will feel both benefits directly: the starter app reaches you as a repository with history, and every lab session ends with your own work committed — a checkpoint you can always return to.

The model

Git's model: distributed, and snapshots rather than diffs

Two design decisions distinguish git from its predecessors. First, git is distributed: every clone of a repository contains the complete history, not a working copy checked out from a central server. You commit, branch and inspect history locally, at local speed, offline; synchronization with other copies is a separate, explicit step. The "central" repository on GitHub is central only by team convention — structurally it is a clone like yours.

Second, git stores snapshots, not differences. Each commit conceptually records the state of the entire project tree at that moment — not a patch relative to the previous version. Under the hood git is a content-addressed database: every stored object — a file's content (blob), a directory listing (tree), a commit — is identified by the cryptographic hash of its content. Identical content is stored once, which is what makes full-tree snapshots cheap; and because every commit's identity includes its parent's hash, history forms a tamper-evident chain — change anything in the past and every hash after it changes. Diffs, when you view them, are computed between snapshots on demand.

Because each commit points to its parent commit (or parents, plural, for merges), history is a directed acyclic graph (DAG) of snapshots. Every other git concept — branches, merging, remotes — is an operation on this graph.

The model

The three areas: working tree, index, repository

Git's day-to-day mechanics revolve around three places a change can be. The working tree is the ordinary folder of files you edit. The index (also called the staging area) is a draft of the next commit: git add copies a file's current state into it. The repository (the hidden .git directory) holds the permanent object database of commits: git commit seals whatever the index contains into a new snapshot. This two-step design is deliberate — it lets you edit freely and then compose a precise, reviewable commit from exactly the changes that belong together, leaving half-done work out.

The lifecycle of a change. git status tells you, at any moment, what sits where.

the everyday loop 
git status                  # what changed, and where does it sit?
git add app/chat.py         # stage exactly what belongs in this commit
git commit -m "Add retry logic to the chat client"
git log --oneline           # the story so far, one line per commit

Commit messages are documentation

A commit message answers why, not just what. Six months from now — or six minutes, when an AI agent reads your history for context — "Fix stuff" helps nobody.

The model

Branches, HEAD and refs

Here is the insight that makes git's branching famously cheap: a branch is not a copy of anything. It is a ref — a 41-byte file containing the hash of one commit. Creating a branch creates that pointer; committing on a branch simply moves the pointer forward to the new snapshot. HEAD is the special ref marking where you currently are — normally it points at a branch, so your next commit advances that branch. Switching branches (git switch) repoints HEAD and rewrites your working tree to match the target snapshot.

← feature/rag · HEAD

Two branches: work diverged after C3. Each branch name is just a pointer to the tip of its line; HEAD marks the one you're on.

The practical convention this enables: main stays releasable, and each unit of work — a feature, a fix, an experiment — happens on its own short-lived branch, merged back when ready. Cheap branches are also what make AI-assisted development safe: give an agent its own branch, review the result, and merging is a decision rather than an accident.

branching 
git switch -c feature/rag     # create the branch and move HEAD onto it
# ... edit, add, commit as usual — main is untouched ...
git switch main               # back to the stable line
git branch                    # list branches; * marks HEAD
The model

Merging: bringing lines of work back together

Merging reunites diverged branches, and git distinguishes two cases. If the target branch has not moved since the feature branched off, git performs a fast-forward: it simply slides the branch pointer ahead — no new commit, because no reconciliation was needed. If both lines advanced, git performs a three-way merge: it compares the two tips against their common ancestor in the DAG and combines the changes into a new merge commit with two parents — the graph joins back together.

When both branches changed the same lines, git cannot decide for you and declares a conflict: the file is marked up with both versions between <<<<<<< and >>>>>>> markers, and you resolve it by editing the file to the correct final state, staging it, and completing the merge. Conflicts are not failures — they are the system refusing to guess about genuinely ambiguous intent.

merging 
git switch main
git merge feature/rag         # fast-forward, or three-way merge with a merge commit
# if conflicts: edit the marked files, then
git add app/chat.py
git commit                    # completes the merge

Merge vs rebase — the same result, two different histories

Git offers a second way to bring branches together, and the choice between them is the most-argued question in everyday git use. Both end with your work combined with main; they differ entirely in what the history looks like afterwards, and therefore in what a future reader can reconstruct.

Start from the situation that makes the two visible. You branched at C3 and wrote D1 and D2. Meanwhile main moved on with C4 and C5. The lines have diverged — this is the normal state of any team:

Merge — record that the lines met

git merge creates one new commit, M, whose two parents are C5 and D2. Nothing that already existed is touched: D1 and D2 keep their identity, their hashes and their original timestamps. The graph forks and re-joins, and that fork is permanently visible — which is exactly the point. The history now records a fact about how the work happened: this branch existed, it ran in parallel with that one, and here is where they were reconciled.

Rebase — retell the story as if it happened later

git rebase main does something fundamentally different: it takes the changes introduced by D1 and D2, rewinds your branch to C5, and applies those changes again on top. The results are new commits — conventionally drawn D1′ and D2′ — with different hashes, different parents and a new committer timestamp. The originals are not modified; they are abandoned, left unreferenced until git's garbage collection removes them.

3c2b1a0  HEAD@{1}: rebase (start): checkout main    ← the pre-rebase tip

Read those two diagrams together and the trade is plain. Merge preserves what actually happened at the cost of a graph that forks; rebase produces a history that is easier to read at the cost of being partly fiction — the commits claim to have been written on top of C5, and they were not. Neither is dishonest in any meaningful sense; they optimize for different readers.

Which leads to the one rule worth memorizing, known widely as the golden rule of rebasing: never rebase commits that exist outside your own machine. The reason follows directly from the diagram — after a rebase your branch has different commits than the copy your colleague fetched. Their git sees two unrelated lines of development, and an innocent git pull merges both, duplicating every commit. If you have already pushed and truly must rebase, you are forcing a rewrite on everyone (git push --force-with-lease) and you owe the team a warning first.

The workflow most teams settle on uses both, each where it is safe: rebase privately to clean up your own branch before opening a pull request — squashing "fix typo" commits, reordering, rewriting messages — and then merge that branch into main, so the integration point is recorded. A common variant on hosting platforms is the squash merge, which collapses the whole branch into one commit on main: maximally readable history, at the cost of losing the individual steps entirely.

the two commands, and the safe rebase workflow 
# MERGE — bring a finished branch into main (safe, always)
git switch main
git pull
git merge feature/rag

# REBASE — tidy YOUR OWN branch onto the latest main before review
git switch feature/rag
git fetch origin
git rebase origin/main          # replay my commits on top of current main
# conflicts? resolve, then:
git add <file>
git rebase --continue           # ...or `git rebase --abort` to undo everything

# only if the branch was already pushed AND is yours alone:
git push --force-with-lease     # safer than --force: refuses if someone else pushed

If a rebase goes wrong

Nothing is lost. git rebase --abort restores the pre-rebase state mid-operation, and afterwards git reflog lists every position HEAD has held — git reset --hard HEAD@{3} returns you there. The reflog is git's undo history, and it is the reason experienced users experiment fearlessly.

The model

Remotes & collaboration

A remote is another copy of the repository that yours knows by name — conventionally origin, the copy on a hosting service such as GitHub, GitLab or Azure DevOps. git clone <url> creates your local copy and wires up origin automatically. From then on, synchronization is explicit and two-directional: git fetch downloads new commits from the remote without touching your work; git pull is fetch plus merging the remote branch into yours; git push uploads your commits. Nothing moves unless you ask — which is why git works on a plane, and why "it's committed" and "it's pushed" are different statements.

Hosting services add the collaboration layer on top of the protocol, centered on the pull request (PR): a proposal to merge one branch into another, packaged with the diff, a discussion thread, review and approval, and usually automated checks. The PR is where teams enforce quality — human review, tests, and increasingly AI review — before anything reaches main. In practice

If you learn one habit

Run git status before and after anything you're unsure about. Nearly every git confusion dissolves once you can see which of the three areas a change is sitting in.
